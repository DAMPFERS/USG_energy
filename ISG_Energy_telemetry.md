# Телеметрия энергосистемы купола для ЦУП

Для управления линиями нужно, чтобы в одной локальной сети с умным щитком был запущен сервер (занимается фактическим управлением линиями, задает игровые сценарии, предоставляет интерфейс). Для получения данных телеметрии необходимо подключиться к этому серверу:

Сервер отдаёт данные двумя способами:

| Способ | Адрес | Когда использовать |
|---|---|---|
| **WebSocket (поток)** | `ws://<сервер>:8000/ws/telemetry` | основной канал: сервер сам присылает срез каждые 2 с и сообщения терминала |
| **HTTP REST (опрос)** | `http://<сервер>:8000/api/telemetry...` | если WebSocket неудобен, для разовых запросов, для загрузки истории и прогноза |

Все ответы — JSON в кодировке UTF-8. Подключение только на чтение: через телеметрию нельзя
управлять линиями или АКБ.

> **Версия формата — `schema: 2`.** По сравнению с `schema: 1`: время купола марсианское (`mars`),
> аккумулятор один (`battery` вместо `batteries[]` / `active_battery`), коридор заменён на `limits`,
> у линий есть `priority`, добавлены `alarms` и пропуски связи `gaps` в истории, убрано поле `phase`.

---

## 1. Подключение

### Адрес

* Хост и порт — IP компьютера, на котором запущен сервер энергосистемы, порт по умолчанию `8000`
  (`config/server.yaml`: `host`, `port`).
* Компьютер ЦУП должен быть в той же сети и видеть этот порт.

### CORS

Если панель ЦУП — веб-страница с другого адреса, GET-запросы из браузера разрешены
(`telemetry.cors_origins`, по умолчанию `["*"]`). На WebSocket CORS не действует.

## 2. Единицы и соглашения

| Величина | Единица | Поле |
|---|---|---|
| Мощность | Вт | `*_w` |
| Ток | А | `*_a` |
| Ёмкость / заряд АКБ | А·ч | `*_ah` |
| Напряжение | В | `voltage_v` |
| Время купола | марсианское: `sol` + `time` (`HH:MM[:SS]`), `t` — минуты от Сола 1 00:00 | `mars`, `t`, `sol`, `time` |
| Земное время | ISO 8601 без часового пояса (местное время сервера) | `earth_time` |
| Метка отправки | Unix-время, секунды (дробное) | `ts` |

Важно:

* **Марсианское время.** Игра идёт 50 часов: начало 27.10 в 11:30 земного времени = Сол 1, 11:30.
  Сол длится **24 ч 40 мин**: после 23:59 часы показывают 24:00…24:39, затем начинается следующий сол
  с 00:00. Конец игры — Сол 3, 12:10.
* `t` — минуты от начала Сола 1 (00:00) с дробной частью, непрерывная шкала через все солы
  (`t = (sol − 1) × 1480 + минуты от начала сола`). Удобно для оси X графиков.
  Длина сола в минутах — `sol_min` в `hello`.
* **Мощности игровые** — это мощности купола, которые видят участники (кВт купола × 1000).
  На реальных реле стоит множитель `scale`: лампа 60 Вт может соответствовать 1200 Вт купола.
  Реально измеренные реле значения передаются отдельно в `lines[].measured`.
* **Ток и А·ч АКБ** пересчитываются из мощности и энергии через номинальное напряжение
  (`telemetry.battery_voltage_v`, сейчас 24 В): `I = P / U`, `А·ч = Вт·ч / U`.
* **Знак тока и мощности АКБ:** `> 0` — заряд, `< 0` — разряд.
* При отладке (`clock.mode: sim`) время купола идёт быстрее (`speed`, например ×20), поэтому для оси X
  используйте `t`, а не `ts`.

## 3. WebSocket `/ws/telemetry`

```
ws://<сервер>:8000/ws/telemetry
ws://<сервер>:8000/ws/telemetry?token=<токен>
```

### Что присылает сервер

Каждое сообщение — JSON-объект с полем `type`:

| `type` | Когда | Содержимое |
|---|---|---|
| `hello` | сразу после подключения | справочник: линии, источники, АКБ, границы игры — см. [5.2](#52-справочник-get-apitelemetrymeta--hello) |
| `forecast` | сразу после `hello` | прогноз генерации W(t) на всю игру, шаг 5 мин — см. [5.3](#53-прогноз-генерации-wt-get-apitelemetryforecast) |
| `telemetry` | каждые `push_interval_s` (сейчас 2 с, приходит в `hello`) | текущий срез — см. [5.1](#51-текущий-срез-get-apitelemetry--telemetry) |
| `message` | при новом сообщении терминала | события игры: предупреждения, блэкаут, отключения — см. [3.2](#32-сообщения-терминала-message) |
| `pong`, `history`, `error` | в ответ на запросы клиента | см. ниже |

### 3.1. Запросы клиента

Клиент может отправлять JSON-запросы в тот же сокет. Отвечать на них не обязательно, поток идёт и так.

| Запрос | Ответ |
|---|---|
| `{"type": "ping"}` | `{"type": "pong", "ts": 1791363252.264}` |
| `{"type": "get_meta"}` | сообщение `hello` |
| `{"type": "get_forecast", "from": "2 12:00", "to": "2 16:00", "step_min": 5}` | сообщение `forecast` (все поля, кроме `type`, необязательны; время — «сол ЧЧ:ММ») |
| `{"type": "get_history", "since": 1600.0}` | сообщение `history` — точки с `t > since` (без `since` — вся игра) |

Неизвестный или некорректный запрос: `{"type": "error", "error": "..."}`. Соединение при этом не закрывается.

### 3.2. Сообщения терминала (`message`)

```json
{"type": "message", "n": 42, "ts": "2026-10-28 13:40:00", "mars": "Sol 2 13:00:00", "level": "CRIT",
 "text": "DUST STORM. Solar panel output has dropped sharply. Reduce the load to the minimum."}
```

`level`: `INFO`, `WARN`, `CRIT`, `OK`. `n` — сквозной номер сообщения за игру, `ts` — земное время,
`mars` — марсианское. Тексты сообщений — на английском (их же видят участники).
В поток попадают только сообщения, появившиеся после подключения. Весь журнал можно получить
через `GET /api/terminal?after=0` (без токена, это API панели участников).

### 3.3. Переподключение

Если сервер перезапустили или пропала сеть, соединение закроется. Переподключайтесь с паузой 2–5 с.
После переподключения снова придут `hello` и `forecast`. Пропущенные точки графика можно догрузить
запросом `get_history` с `since` = последний полученный `t`.

Если сервер был выключен, игра после запуска продолжается с текущего реального момента. Промежуток,
когда сервер не работал, приходит в истории в `gaps` — на графике его стоит показать как потерю связи.

## 4. HTTP REST

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/api/telemetry` | — | текущий срез (как `telemetry` в WebSocket) |
| GET | `/api/telemetry/meta` | — | справочник (как `hello`, без поля `type`) |
| GET | `/api/telemetry/forecast` | `from=<сол ЧЧ:ММ>`, `to=<сол ЧЧ:ММ>`, `step_min=5` | прогноз W(t) |
| GET | `/api/telemetry/history` | `since=<t>` | история игры с шагом `history_step_s` (30 с времени купола) + `gaps` |

Все параметры необязательны. По умолчанию прогноз строится на всю игру (Сол 1 11:30 – Сол 3 12:10)
с шагом `telemetry.forecast_step_min` (5 мин). В URL пробел в `from`/`to` кодируется как `%20`:
`?from=2%2012:00`.

Коды ответа:

* `200` — успешно;
* `400` — неверные параметры (например, `step_min=0` или больше 2000 точек);
* `403` — неверный токен;
* `503` — сервер только что запустился и ещё не посчитал первый такт, повторите через секунду.

Данные обновляются раз в `engine_tick_s` (сейчас 2 с), чаще опрашивать `/api/telemetry` смысла нет.

## 5. Форматы данных

### 5.1. Текущий срез: `GET /api/telemetry` / `telemetry`

```json
{
  "type": "telemetry",
  "schema": 2,
  "seq": 1532,
  "ts": 1792614885.811,
  "earth_time": "2026-10-27T14:07:35",
  "mars": {"t": 847.583, "sol": 1, "time": "14:07:35"},
  "game_status": "running",

  "generation": {
    "total_w": 9860.0,
    "sources": [
      {"id": "solar", "name": "Solar panels", "type": "solar",
       "power_w": 9860.0, "forecast_w": 10130.6, "sigma_w": 820.0}
    ]
  },

  "consumption": {"total_w": 7667.0},
  "limits": {"max_w": 9000.0, "min_w": 4860.0, "max_charge_w": 5000.0, "max_discharge_w": 6000.0},
  "balance_w": 2193.0,
  "deficit_w": 0.0,
  "alarms": [],

  "lines": [
    {"id": 1, "key": "HAB1-S", "name": "HAB 1 · Sockets", "on": false, "online": true,
     "status": "tripped", "priority": 13, "power_w": 0.0,
     "reason": "Load shedding: power deficit", "until": "14:20", "until_t": 860.32,
     "measured": {"power_w": 0.0, "voltage_v": 230.0, "current_a": 0.0}},
    {"id": 12, "key": "BIO-L", "name": "BIOLAB · Lighting", "on": true, "online": true,
     "status": "on", "priority": 4, "power_w": 951.0, "reason": null, "until": null, "until_t": null,
     "measured": {"power_w": 47.5, "voltage_v": 229.8, "current_a": 0.207}}
  ],

  "battery": {
    "name": "Dome battery", "status": "connected", "off_until": null, "voltage_v": 24.0,
    "capacity_ah": 1666.67, "available_ah": 1072.79, "soc_pct": 64.4,
    "current_a": 91.38, "power_w": 2193.0, "mode": "charge",
    "max_charge_a": 208.33, "max_discharge_a": 250.0
  }
}
```

#### Общие поля

| Поле | Описание |
|---|---|
| `schema` | версия формата (сейчас `2`). Добавление новых полей версию не меняет |
| `seq` | номер среза, растёт с каждым срезом |
| `ts` | момент формирования среза на сервере, Unix-время |
| `earth_time` | земное время купола (ISO 8601, местное время) |
| `mars` | марсианское время: `t`, `sol`, `time` (`HH:MM:SS`, часы могут быть 24) |
| `game_status` | `before` — игра ещё не началась, `running` — идёт, `finished` — закончилась. Вне `running` баланс не считается, ток АКБ = 0 |

#### Генерация `generation`

| Поле | Описание |
|---|---|
| `total_w` | суммарная генерация, Вт |
| `sources[]` | генерация по источникам. Сейчас один источник — `solar` (солнечные панели). Реактор позже появится отдельным элементом (`"type": "reactor"`), формат не изменится — **не завязывайтесь на то, что источник один** |
| `sources[].power_w` | фактическая генерация источника, Вт |
| `sources[].forecast_w` | прогноз на текущий момент, Вт (для сравнения факт/прогноз) |
| `sources[].sigma_w` | ожидаемый разброс прогноза (1σ), Вт |

#### Потребление, границы и баланс

| Поле | Описание |
|---|---|
| `consumption.total_w` | суммарное потребление включённых линий, Вт |
| `limits.max_w` | верхняя граница потребления, Вт. Задаётся на всю игру, организатор может изменить. Превышение дольше 5 мин — блэкаут (все линии выключаются) |
| `limits.min_w` | нижняя граница потребления, Вт = генерация − `max_charge_w`. `null`, если не действует (АКБ отключён или полностью заряжен — тогда излишек просто теряется). Потребление ниже неё дольше 5 мин — АКБ отключается на 15 мин |
| `limits.max_charge_w`, `max_discharge_w` | предельные мощности заряда и разряда АКБ, Вт |
| `balance_w` | генерация − потребление. `> 0` — излишек идёт в АКБ, `< 0` — АКБ разряжается |
| `deficit_w` | мощность, которую не покрыли ни генерация, ни АКБ. `> 0` — через 10 с линии начнут отключаться по приоритету |
| `alarms[]` | идущие обратные отсчёты: `kind` (`overload` — перегруз, `surplus` — избыток выше мощности заряда, `deficit` — дефицит), `title`, `left_s` — сколько реальных секунд осталось до последствия |

#### Линии `lines[]`

| Поле | Описание |
|---|---|
| `id` | номер линии (реле), 1–13 |
| `key` | ключ потребителя (`HAB1-S`, `BIO-L`, … — см. [5.5](#55-линии-и-потребители)) или `null`, если линия ни к кому не привязана |
| `name` | название потребителя на английском (как у участников), например `HAB 1 · Sockets` |
| `on` | реле включено (`true`) / выключено (`false`) |
| `online` | реле отвечает. Если `false`, мощность линии неизвестна и в сумму не входит |
| `status` | `on`, `off`, `locked` (заблокирована организатором), `tripped` (отключена при дефиците и заблокирована), `offline` (нет связи с реле) |
| `priority` | приоритет 1–13, его задают участники. При дефиците линии отключаются от 13 к 1 |
| `power_w` | потребляемая мощность линии, Вт купола (0, если выключена) |
| `reason`, `until`, `until_t` | причина блокировки, марсианское время `HH:MM` и `t`, до которого она действует (для `locked`/`tripped`), иначе `null` |
| `measured` | реальные показания реле: `power_w` (Вт), `voltage_v` (В), `current_a` (А). `null`, если реле не на связи |

#### Аккумулятор `battery`

| Поле | Описание |
|---|---|
| `name` | название |
| `status` | `connected` — работает, `disconnected` — отключён (после превышения мощности заряда или организатором) до `off_until` (марсианское `HH:MM`) |
| `voltage_v` | номинальное напряжение, по которому считаются ток и А·ч |
| `available_ah` | **доступная ёмкость** (текущий запас заряда), А·ч |
| `capacity_ah` | полная ёмкость, А·ч |
| `soc_pct` | уровень заряда, % |
| `current_a` | **ток заряда/разряда**, А: `> 0` — заряд, `< 0` — разряд |
| `power_w` | то же в Вт |
| `mode` | `charge`, `discharge`, `idle` |
| `max_charge_a`, `max_discharge_a` | предельные токи заряда и разряда, А |

### 5.2. Справочник: `GET /api/telemetry/meta` / `hello`

Приходит один раз при подключении. Нужен, чтобы заранее построить интерфейс: список линий,
источников, АКБ, границы игры для оси X.

```json
{
  "type": "hello",
  "schema": 2,
  "name": "ISG 2026 — Mars dome",
  "scenario": "mission",
  "sol_min": 1480.0,
  "start": {"t": 690.0, "sol": 1, "time": "11:30:00"},
  "end": {"t": 3690.0, "sol": 3, "time": "12:10:00"},
  "clock": {"mode": "real", "speed": 1.0},
  "push_interval_s": 2.0,
  "lines": [
    {"id": 1, "name": "HAB 1 · Sockets", "key": "HAB1-S", "priority": 13},
    {"id": 2, "name": "HAB 2 · Sockets", "key": "HAB2-S", "priority": 2},
    "…",
    {"id": 13, "name": "MAIN · Lighting", "key": "MAIN-L", "priority": 1}
  ],
  "sources": [{"id": "solar", "name": "Solar panels", "type": "solar"}],
  "battery": {"name": "Dome battery", "voltage_v": 24.0, "capacity_ah": 1666.67}
}
```

`lines` всегда содержит все 13 линий. Названия, ключи и приоритеты — на момент запроса,
актуальные значения приходят в каждом срезе (см. [5.5](#55-линии-и-потребители)).

### 5.3. Прогноз генерации W(t): `GET /api/telemetry/forecast`

Прогноз мощности солнечных панелей на всю игру с ожидаемым разбросом. Прогноз задан заранее
(шаг 5 мин) и за игру не меняется, поэтому его достаточно загрузить один раз.

```
GET /api/telemetry/forecast                                  вся игра, шаг 5 мин
GET /api/telemetry/forecast?from=2%2011:00&to=2%2017:00&step_min=10
```

```json
{
  "type": "forecast",
  "schema": 2,
  "source": "solar",
  "step_min": 5.0,
  "from": "Sol 1 11:30",
  "to": "Sol 3 12:10",
  "points": [
    {"t": 690.0, "sol": 1, "time": "11:30", "forecast_w": 11560.0, "sigma_w": 800.0, "low_w": 10760.0, "high_w": 12360.0},
    {"t": 695.0, "sol": 1, "time": "11:35", "forecast_w": 11630.0, "sigma_w": 800.0, "low_w": 10830.0, "high_w": 12430.0}
  ]
}
```

| Поле | Описание |
|---|---|
| `t`, `sol`, `time` | момент времени купола: минуты от Сола 1 00:00, номер сола и `HH:MM` |
| `forecast_w` | ожидаемая генерация W(t), Вт |
| `sigma_w` | неопределённость прогноза (1σ), Вт. Растёт там, где ожидается облачность или буря |
| `low_w`, `high_w` | границы коридора `forecast_w ± sigma_w` (нижняя не ниже 0) — для заливки на графике |

Рекомендуемый график: линия `forecast_w`, полупрозрачная заливка между `low_w` и `high_w`,
поверх — фактическая генерация из `history` и потока `telemetry` (`generation.sources[].power_w`).

> Фактическая генерация может отличаться от прогноза: организатор может изменить масштаб генерации
> по ходу игры, и прогноз этого заранее не показывает. Это часть игры.

### 5.4. История: `GET /api/telemetry/history`

Записи с начала игры с шагом `step_s` (30 с времени купола). Нужна, чтобы при открытии
панели ЦУП сразу нарисовать графики за прошедшее время, а дальше дополнять их живыми срезами.

```
GET /api/telemetry/history                все точки
GET /api/telemetry/history?since=1600.5   только точки с t > 1600.5
```

```json
{
  "type": "history",
  "schema": 2,
  "step_s": 30.0,
  "samples": [
    {"t": 847.583, "sol": 1, "time": "14:07",
     "generation_w": 9860.0, "consumption_w": 7667.0,
     "limits": {"max_w": 9000.0, "min_w": 4860.0},
     "lines_w": {"1": 0.0, "2": 951.0, "3": 0.0, "4": 562.0, "5": 673.0, "6": 1015.0, "7": 1346.0,
                 "8": 383.0, "9": 820.0, "10": 687.0, "11": 955.0, "12": 276.0, "13": 310.0},
     "battery_ah": 1072.79, "battery_a": 91.38, "battery_connected": true}
  ],
  "gaps": [
    {"from": {"t": 742.282, "sol": 1, "time": "12:22:16"}, "to": {"t": 753.289, "sol": 1, "time": "12:33:17"}}
  ]
}
```

`lines_w` — мощность каждой линии (ключ — `id` линии строкой, `"1"`–`"13"`), `battery_ah` — доступная
ёмкость АКБ, `battery_a` — ток (`+` заряд). `limits.min_w` = `null`, если нижняя граница в этот момент
не действовала. В истории линии идут по номерам; чтобы подписать их, берите `name`/`key` из `hello`.

`gaps` — промежутки, когда сервер не работал (между соседними точками больше нескольких шагов).
Данных за них нет; линии графика на этих участках стоит разрывать и помечать «потеря связи».
`gaps` всегда приходят целиком, независимо от `since`.

### 5.5. Линии и потребители

В куполе 13 линий (реле). Каждая питает одного потребителя:

| `key` | `name` | Что это |
|---|---|---|
| `HAB1-S` | HAB 1 · Sockets | розетки жилого модуля HAB 1 |
| `HAB2-S` | HAB 2 · Sockets | розетки жилого модуля HAB 2 |
| `FAB-S1` | FABLAB · Sockets 1 | розетки FABLAB (мастерская), линия 1 |
| `FAB-S2` | FABLAB · Sockets 2 | розетки FABLAB (мастерская), линия 2 |
| `BIO-S1` | BIOLAB · Sockets 1 | розетки BIOLAB, группа 1 |
| `BIO-S2` | BIOLAB · Sockets 2 | розетки BIOLAB, группа 2 |
| `MAIN-S1` | MAIN · Sockets 1 | розетки главного модуля MAIN, линия 1 |
| `MAIN-S2` | MAIN · Sockets 2 | розетки главного модуля MAIN, линия 2 |
| `HAB1-L` | HAB 1 · Lighting | освещение жилого модуля HAB 1 |
| `HAB2-L` | HAB 2 · Lighting | освещение жилого модуля HAB 2 |
| `FAB-L` | FABLAB · Lighting | освещение FABLAB |
| `BIO-L` | BIOLAB · Lighting | освещение BIOLAB |
| `MAIN-L` | MAIN · Lighting | освещение MAIN |

**Какое реле (`id`) питает какого потребителя, определяется на площадке при монтаже**, и организатор
может поменять привязку в любой момент. Поэтому:

* опознавайте потребителя по `key`, а не по `id`: `id` — это номер реле, он не несёт смысла;
* не кэшируйте соответствие `id → key` навсегда — берите его из каждого среза (`lines[].key`)
  или перезапрашивайте `get_meta` / `GET /api/telemetry/meta`;
* в истории (`lines_w`) данные хранятся по `id` реле. Если привязку поменяли в течение игры,
  старые точки остаются за тем же реле.

Чтобы сгруппировать данные по модулям, разбирайте `key`: префикс `MAIN`, `FAB`, `BIO`, `HAB1`, `HAB2` —
модуль, суффикс `S…` — розетки, `L` — освещение.

### Python (WebSocket)


```python
import asyncio
import json

import websockets

URL = "ws://192.168.1.50:8000/ws/telemetry"   # + "?token=..." если задан токен


async def main():
    while True:
        try:
            async with websockets.connect(URL) as ws:
                async for raw in ws:
                    msg = json.loads(raw)
                    if msg["type"] == "hello":
                        print("Подключено:", msg["name"])
                    elif msg["type"] == "forecast":
                        print("Прогноз:", len(msg["points"]), "точек")
                    elif msg["type"] == "telemetry":
                        m, bat = msg["mars"], msg["battery"]
                        print(f'Сол {m["sol"]} {m["time"]}  ген {msg["generation"]["total_w"]:.0f} Вт  '
                              f'потр {msg["consumption"]["total_w"]:.0f} Вт  '
                              f'АКБ: {bat["available_ah"]:.1f} А·ч, {bat["current_a"]:+.1f} А')
                    elif msg["type"] == "message":
                        print(f'[{msg["mars"]}] [{msg["level"]}] {msg["text"]}')
        except (OSError, websockets.ConnectionClosed) as e:
            print("Нет связи:", e, "— переподключение через 3 с")
            await asyncio.sleep(3)


asyncio.run(main())
```

### JavaScript (браузер)

```js
const URL = 'ws://192.168.1.50:8000/ws/telemetry';

function connect() {
  const ws = new WebSocket(URL);
  ws.onmessage = (e) => {
    const msg = JSON.parse(e.data);
    switch (msg.type) {
      case 'hello':     /* построить список линий из msg.lines, ось X — msg.start.t … msg.end.t */ break;
      case 'forecast':  /* нарисовать W(t) из msg.points */ break;
      case 'telemetry': /* обновить показатели и добавить точку на график по msg.mars.t */ break;
      case 'message':   /* вывести событие msg.mars / msg.level / msg.text */ break;
    }
  };
  ws.onclose = () => setTimeout(connect, 3000);   // переподключение
}
connect();
```

## 7. Соответствие запросу ЦУП

| Что запросил ЦУП | Где взять |
|---|---|
| Состояние линий вкл/выкл | `lines[].on`, подробнее — `lines[].status`; чья линия — `lines[].key` / `name` |
| Потребляемая мощность линий, Вт | `lines[].power_w`, сумма — `consumption.total_w` |
| Текущая генерация по источникам, Вт | `generation.sources[].power_w` (сейчас `solar`), сумма — `generation.total_w` |
| АКБ: доступная ёмкость, А·ч | `battery.available_ah` |
| АКБ: ток заряда/разряда, А | `battery.current_a` (`+` заряд, `−` разряд) |
| Прогноз генерации W(t) для графика | сообщение `forecast` / `GET /api/telemetry/forecast` |
| История для графиков | `GET /api/telemetry/history` или запрос `get_history` (пропуски связи — `gaps`) |
